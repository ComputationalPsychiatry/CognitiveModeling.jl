Fitting with Turing.jl

The Turing.jl models of the sessions on the page Fitting, what a model can add for them, and reading the trajectories they saved from a chain.

Turing.jl models

full_model, session_model and multiple_sessions_model make these models when they are given TuringBackend(). The models are public, but not exported.

CognitiveModeling.TuringBackend — Type
TuringBackend()

Marker of Turing.jl as the inference backend, which full_model, session_model and multiple_sessions_model take to make Turing.jl models. This needs Turing.jl to be loaded.

source
CognitiveModeling.full_model — Method
full_model(::TuringBackend, sessions_info::MultipleSessionsInfo,
           cognitive_parameters_model;
           environment_parameters_model=NoParameters(),
           downstream_model=NoDownstreamModel(), fixed_cognitive_parameters=(;),
           fixed_environment_parameters=(;), parallelization=SerialSessions(),
           include_submodel_prefixes=false)

Create the Turing.jl model which fits a cognitive model to several sessions, in three parts: cognitive_parameters_model gives or samples the cognitive parameters of every session, and environment_parameters_model those of the environment model, the sessions in sessions_info run with them as turing_multiple_behavioral_sessions, and downstream_model can do something with the trajectories they saved, such as a regression of a measurement on a state. The parts are prepared with prepare_full_model, and the model is turing_full_model of the prepared parts. This needs Turing.jl to be loaded.

Arguments

  • sessions_info::MultipleSessionsInfo: the sessions, prepared once with MultipleSessionsInfo.
  • cognitive_parameters_model: the parameter model of the cognitive model, which gives or estimates its parameters for every session: a subtype of AbstractParametersModel, such as IndependentParameters with a prior for each parameter. A tuple of parameter models, or a NamedTuple of them, is made into a CompositeParameters of them, with each part of a NamedTuple under its name. So is a tuple or a NamedTuple given as environment_parameters_model.
  • environment_parameters_model=NoParameters(): the parameter model of the environment model of the sessions, when they have one. By default the environment's parameters take its default values, and FixedParameters gives others. When they are estimated, every session includes its environment, also those with nothing to impute, so that the observations in the data inform them, which is an error for a session prepared with include_environment = false. Sessions without an environment take no parameters.
  • downstream_model=NoDownstreamModel(): a final submodel which is run after the sessions, such as for correlations with other kinds of data: a subtype of AbstractDownstreamModel. The default samples nothing.
  • fixed_cognitive_parameters::NamedTuple=(;) and fixed_environment_parameters::NamedTuple=(;): values which every session gets for the parameters they name, such as (; initial_value = 0.3), while the parameter models give the others. A parameter is either fixed here or given by its parameter model, and a fixed parameter must be one in the model's attributes.
  • parallelization=SerialSessions(): whether the sessions run over the threads Julia was started with, with ParallelSessions(). The model must then be marked with setthreadsafe(model, true) from DynamicPPL before it is sampled: without the mark, a threaded model has a wrong log density with no error, so the sessions throw an error instead.
  • include_submodel_prefixes::Bool=false: whether the variables of the two parameter models and of the downstream model are named under cognitive_parameters_model, environment_parameters_model and downstream_model. Without the prefixes, the names are shorter, but a variable of the same name in two of them is one variable, which sample refuses with an error, and which a log density gives one value with both priors counted. A warning says so when the model is made, when the cognitive model and the environment model have a parameter of the same name and both parameter models sample.

The variables of a parameter model are named after the parameters, such as learning_rate.sessions with IndependentParameters, where learning_rate.sessions[3] is the learning rate of the third session, or under the parameter model's name with include_submodel_prefixes = true. A part of a CompositeParameters that is given with a name has its variables under that name. The variables of the sessions are under sessions[i], and those of the downstream model as it names them, or under downstream_model with the prefixes. rand(model) shows every variable's name.

The model returns a NamedTuple with cognitive_parameters, environment_parameters, saved_trajectories and downstream_values: the cognitive parameters and the environment parameters of every session as the parameter models gave them, the trajectories each session saved, as turing_multiple_behavioral_sessions returns them, and what the downstream model returned. returned(model, chain) gives them for each sample, so a fitted state is read from the chain without simulating again.

When a cognitive model or an environment model sets parameters_valid to false in its ModelOutput, or a stopping_criterion is met while the data of a session continues, as SessionInfo describes, the session gives the parameters a log density of -Inf, so that a sampler rejects them, and ends before that timestep without scoring the data. The trajectories of that session then end before the timestep, its saved_trajectories has parameters_valid = false, and the downstream model doesn't run, so downstream_values is nothing. A criterion that is met already before the first timestep of a session is an error instead, which stops a fit.

Such a sample doesn't have the variables that come after that timestep: the values that the later timesteps impute, simulate or sample, and the variables of the downstream model. A fit of a model with such variables can then fail when it starts, since Turing.jl takes the variables of a model from one draw from the prior, whatever initial_params it is given. A chain sampled from the prior, and the predictions of predict, have missing for those variables in such samples. A model that samples a variable within a timestep on some timesteps only, chosen by its parameters or its state, can fail in the same way, or give a wrong posterior without an error. The page Fitting with Turing.jl describes when this happens, and what to do.

Saving states adds a cost to gradient calculations. Without a downstream model that needs them, a fit is fastest with sessions that save nothing, and the trajectories are then read from the chain afterwards with get_session_trajectories, or with returned on the model of a copy of the sessions that saves them, MultipleSessionsInfo(sessions_info; save_cognitive_trajectories = SaveTrajectories(; states = :expected_reward)), since the two models have the same variables. A warning says so when the sessions save anything and there is no downstream model.

Examples

using CognitiveModeling
using Turing

#The data of two sessions, as a table with one vector for each column
table = (;
    id = ["S1", "S1", "S1", "S2", "S2", "S2"],
    reward = [1.0, 0.0, 1.0, 0.0, 0.0, 1.0],
    choice = [true, false, true, false, missing, true],
)

#The sessions, with the RescorlaWagner model of turing_behavioral_session
sessions_info = MultipleSessionsInfo(
    RescorlaWagner(),
    table;
    observation_columns = :reward,
    action_columns = :choice,
    session_columns = :id,
    who_starts = EnvironmentStarts(),
    save_cognitive_trajectories = SaveTrajectories(; states = :expected_reward),
)

#Each session has its own parameters, from the same priors
cognitive_parameters_model = IndependentParameters((;
    learning_rate = Beta(2, 2),
    inverse_temperature = LogNormal(0, 1),
))

model = full_model(TuringBackend(), sessions_info, cognitive_parameters_model)
chain = sample(model, NUTS(), 1000)

#The parameters and the expected rewards of every session, for each sample
returned_values = returned(model, chain)
returned_values[1].cognitive_parameters.learning_rate
returned_values[1].saved_trajectories[2].states

#The same fit without saving, and the states read from the chain afterwards
sessions_without_saving = MultipleSessionsInfo(
    sessions_info; save_cognitive_trajectories = SaveTrajectories(),
)
unsaved = full_model(TuringBackend(), sessions_without_saving, cognitive_parameters_model)
chain = sample(unsaved, NUTS(), 1000)
returned_values = returned(model, chain)

CognitiveModeling.turing_behavioral_session — Function
turing_behavioral_session(session_info::SessionInfo, cognitive_parameters)
turing_behavioral_session(session_info::SessionInfo, cognitive_parameters,
                          environment_parameters=(;))

Create a Turing.jl model of one session: the cognitive model in session_info goes through the timesteps of its data with cognitive_parameters, and the actions in the data are scored against the action distributions it gives. The second form is for a session with an environment model, which takes its parameters too. This needs Turing.jl to be loaded.

session_model with TuringBackend() makes this model. It is a building block for a Turing.jl model which samples the parameters, as a submodel with its own prefix: to_submodel(prefix(session_model(TuringBackend(), ...), @varname(session)), false). multiple_sessions_model runs one for each of several sessions, and full_model samples their parameters too.

Arguments

  • session_info::SessionInfo: the data, the models and the settings of the session, prepared once with SessionInfo.
  • cognitive_parameters::NamedTuple: the parameters of the cognitive model, usually the random variables of the model around this one. Those it doesn't have take the values in default_parameters, if the model provides defaults for them.
  • environment_parameters::NamedTuple=(;): the parameters of the environment model, with its default values for those that aren't given, if it provides any. A session without an environment takes none.

What it does

In outline, the model of a session without an environment looks like this. It is not the actual code, which also checks the names and the parameters, and saves what is selected:

#The state where the session starts, which a model can sample
state ~ to_submodel(turing_initialize_state(cognitive_model, cognitive_parameters))

for t in 1:n_timesteps

    #The cognitive model gives a distribution for each action, under the prefix timesteps[t]
    output ~ to_submodel(turing_timestep_model(cognitive_model, context))

    #An action that is missing in the data is a latent variable with that distribution
    choice.imputed ~ output.output_distribution.choice
end

#The actions in the data are scored once, against the distributions of their timesteps
actions_to_condition_on ~ product_distribution(action_distributions)

#The parameters as they were given, and the trajectories over the timesteps that the SaveTrajectories select
return (; cognitive_parameters, environment_parameters, saved_trajectories)

A session which includes its environment runs the environment model in the same way on each timestep, before the cognitive model when the environment starts and after it when the agent starts, and scores the observations in the data like the actions.

The states where the session starts come from turing_initialize_state of each model with the parameters, so that a starting state which is a parameter is fitted like any other, and a model can sample its start. Both models are treated the same way on each timestep: turing_timestep_model of the cognitive model runs as a submodel with the prefix timesteps[t], so a model which samples within a timestep has its own variables for each timestep, such as timesteps[3].noise, and an environment model runs with the prefix timesteps[t].environment. The outputs of each, the actions and the observations, are then taken from the data where they are recorded, and where the data has ImputedMissingValue they are imputed from what the model gave: as a latent variable with that distribution, named timesteps[3].choice.imputed or timesteps[3].environment.reward.imputed, or as the value itself if it is a Deterministic. Where the data has SimulatedMissingValue, as in a session from decondition_sessions, they are simulated in the same way, as latent variables named timesteps[3].choice.simulated. Where the data has UnimputedMissingValue, or a marker for nothing happening, the models receive the marker as it is, and nothing is sampled or scored for it. The actions in the data are scored at the end as observed values, in one product over every action and timestep, against the distributions the cognitive model gave for them, which Turing.jl's pointwise_loglikelihoods with factorize = true splits into the log-likelihood of each action, also of outputs whose values aren't numbers. The observations in the data are scored the same way against the distributions the environment gave, so that they inform the missing values and the environment's parameters. A Deterministic is scored as a point mass, with a log density of 0 for its value and -Inf for any other, and only a number or a Bool can be, so a value in the data that the model gives as another kind of Deterministic is an error, and so is one where the model gave nothing, NoValue. When the session doesn't include its environment, as the include_environment of session_info decides, which by default is when nothing in the data is ImputedMissingValue() or SimulatedMissingValue() and the environment's trajectories aren't saved, the session is the same as one without an environment, with the same variables. The stopping_criterion of the models is checked before every timestep, as SessionInfo describes, so that a session from decondition_sessions can end early, as a simulation does.

What it returns

A NamedTuple with cognitive_parameters and environment_parameters, the parameters as they were given, without the default values of the models, and saved_trajectories, the trajectories that the SaveTrajectories of session_info select, which returned(model, chain) gives for each sample. The trajectories are a SessionTrajectories, as simulate_session returns: states, observations, actions and action_distributions of the cognitive model, environment with the states, observations, actions and observation_distributions of the environment when the session has one, which are empty when it didn't run, and NoEnvironment when it has none, and timestep_sizes. Each is a vector with one element for timestep 0, before the first timestep, and one for each timestep that ran. Timestep 0 has the previous observation and action, which are BeforeFirstTimestep unless others are given, BeforeFirstTimestep() for every distribution, and the initial states, which can depend on the parameters. Element t + 1 is then timestep t, and a SaveTrajectories with save_initial_timestep_values = false leaves timestep 0 out. The returned actions and observations are those the models received, with the imputed values. timestep_sizes has the size of each timestep, after BeforeFirstTimestep() for timestep 0 when it is there, when anything is selected, and is empty otherwise. n_timesteps is the number of timesteps that ran, and last_timestep is nothing. parameters_valid is a Bool, whether the parameters stayed valid, also for models that can't set it in their ModelOutput, since a stopping_criterion met while the data continues counts as parameters that turned invalid. When a model sets it to false, or such a criterion is met, the session gives the parameters a log density of -Inf, ends before that timestep and scores nothing, so the trajectories end before it, and the variables of the later timesteps don't exist for that sample, which can keep a sampler from starting, as turing_full_model describes. Any latent variable in a session, imputed or from a model which samples within a timestep, greatly increases the amount of estimated variables, which will generally make fitting the model much slower.

Examples

using CognitiveModeling
using Turing

#The model to fit, a Rescorla-Wagner model with a softmax choice
struct RescorlaWagner <: AbstractCognitiveModel end

function CognitiveModeling.initialize_state(model::RescorlaWagner, parameters)
    return (; expected_reward = parameters.initial_value)
end

function CognitiveModeling.timestep_model(model::RescorlaWagner, context::ModelContext)
    V₋₁ = context.previous_state.expected_reward
    Vₜ = V₋₁ + context.parameters.learning_rate * (context.input.reward - V₋₁)
    Pₜ = BernoulliLogit(context.parameters.inverse_temperature * (Vₜ - 0.5))
    return ModelOutput((; choice = Pₜ), (; expected_reward = Vₜ))
end

function CognitiveModeling.attribute_names(model::RescorlaWagner)
    return ModelAttributes(;
        parameters = (:learning_rate, :inverse_temperature, :initial_value),
        states = :expected_reward,
        inputs = :reward,
        outputs = :choice,
    )
end

CognitiveModeling.default_parameters(model::RescorlaWagner) = (; initial_value = 0.5)

#The data of one session, where the third choice wasn't recorded, prepared once
session_info = SessionInfo(
    RescorlaWagner(),
    (; reward = [1.0, 0.0, 1.0, 1.0]),
    (; choice = [true, false, ImputedMissingValue(), true]);
    who_starts = EnvironmentStarts(),
    save_cognitive_trajectories = SaveTrajectories(; states = :expected_reward),
)

#Priors on the parameters, and the session as a submodel
@model function fit_one_session(session_info)
    learning_rate ~ Beta(2, 2)
    inverse_temperature ~ LogNormal(0, 1)
    session ~ to_submodel(
        prefix(
            session_model(
                TuringBackend(), session_info, (; learning_rate, inverse_temperature)
            ),
            @varname(session),
        ),
        false,
    )
    return session
end

chain = sample(fit_one_session(session_info), NUTS(), 1000)

#The parameters and the expected rewards on each timestep, for each sample
returned_values = returned(fit_one_session(session_info), chain)
returned_values[1].saved_trajectories.states

#The same as chains, which merge into one
parameters = get_session_parameters(returned_values)
trajectories = get_session_trajectories(returned_values)
merge(parameters, trajectories)

CognitiveModeling.turing_multiple_behavioral_sessions — Function
turing_multiple_behavioral_sessions(sessions_info::MultipleSessionsInfo,
                                    cognitive_parameters, environment_parameters=(;),
                                    parallelization=SerialSessions())

Create a Turing.jl model which runs turing_behavioral_session for every session in sessions_info, each with its own cognitive parameters, as a submodel with the prefix sessions[i], so that a latent variable of the third session is named like sessions[3].timesteps[2].choice.imputed. Sessions whose data the model simulates, such as those that decondition_sessions gives, have the prefix simulated_sessions[i] instead, as in simulated_sessions[3].timesteps[2].choice.simulated. Which session i is stands in sessions_info.session_ids[i], and session_index gives i for a data identifier. Environment parameters can only be given when the sessions have an environment model. With ParallelSessions() as parallelization, after the environment parameters, which are (;) for sessions without an environment, the sessions run over the threads Julia was started with. The model that is evaluated, which is the outermost one, must then be marked with setthreadsafe(model, true) from DynamicPPL, since the log density of a threaded model that isn't is wrong with no error; the sessions throw an error when it isn't marked. See parallelization in full_model with TuringBackend(). This needs Turing.jl to be loaded.

cognitive_parameters is a NamedTuple with one vector for each parameter, with one value for every session in the order of sessions_info, which is what a parameter model returns, see turing_parameters_model, and environment_parameters is in the same form. It returns a NamedTuple with cognitive_parameters and environment_parameters as they were given, and saved_trajectories, a vector with the trajectories each session saved, in the same order, as turing_behavioral_session returns them. multiple_sessions_model with TuringBackend() makes this model, and takes parallelization as a keyword. It is a building block for a Turing.jl model which samples the parameters of the sessions in some way of its own, as a submodel without a prefix: to_submodel(multiple_sessions_model(TuringBackend(), sessions_info, parameters), false). full_model does this with parameter models. A model of one's own can return the same NamedTuple, and get_session_trajectories and get_session_parameters then read what it returns too, also when it transforms its variables into the parameters.

Postprocessing

With Turing.jl loaded, which loads FlexiChains.jl, get_session_trajectories and get_session_parameters take a model made by full_model, multiple_sessions_model or session_model with TuringBackend(), and the FlexiChain that sample gives for it. A model of one's own around the sessions gives them the values that returned(model, chain) gives instead, with the MultipleSessionsInfo of several sessions.

chain = sample(model, NUTS(), 1000)
session_trajectories = get_session_trajectories(model, chain; save_cognitive_trajectories = SaveTrajectories(; states = :expected_value))
parameters = get_session_parameters(model, chain)

#The same from a model of one's own around the sessions, which returns what they return
parameters = get_session_parameters(returned(own_model, chain), sessions_info)

Why the package has its own decondition and condition

Turing.jl's decondition and condition work on the variables of a model: condition gives a variable a value, so that the model scores the value instead of sampling it, and decondition takes the value away again. The models of the package don't have the data of their sessions as variables. They take it as arguments, in a SessionInfo or a MultipleSessionsInfo, because the data does more than give values to score:

  • The models receive it on each timestep, as observations and previous actions.
  • It decides how each session runs: its number of timesteps, which values are imputed, whether the environment runs, and where the stopping criterion is checked.
  • It is checked before a fit, against the names and the domains of the models.
  • The observations of a session without an environment have no distribution, so they can only be data.
  • Data in arguments is scored all at once, which makes each evaluation several times faster than values that are looked up by name.

Turing.jl's decondition therefore leaves the data as it is: it can only free variables, and the data aren't variables. decondition_sessions turns the data into variables: it puts SimulatedMissingValue in place of every action, and of every observation when the sessions have an environment, so that the model samples each of them. Turing.jl's sample with Prior() and its predict then simulate the data, as for any model. The deconditioned sessions are named apart from the fitted ones, so that predict draws every variable within them again.

condition_sessions goes the other way: it puts values of those variables back in the data. Turing.jl's condition works on the same variables too, and gives the same posterior for most models, but the values then stay variables. Each is looked up by name on every evaluation, which is slower; a value with a misspelled name is left out without an error; and with a stopping criterion, a session ends where the criterion is met at the parameters of each evaluation, before its last value or after it. With condition_sessions the model is the one that the same data in a table gives: as fast, checked in the same way, with an error for a value that has no place in the data, and with each session ending after its last value.

Together they allow prior and posterior predictive checks and parameter recoveries with Turing.jl's own functions, on the models that the package makes, without writing the simulated data to a table first.

Predictive checks

With Turing.jl loaded, predict_session_trajectories takes a model made by full_model, multiple_sessions_model or session_model with TuringBackend(), and a chain sampled from it. It returns the simulated trajectories as a FlexiChain, as get_session_trajectories makes it. For a prior predictive check, give a chain sampled from the prior, such as sample(model, Prior(), 1000).

chain = sample(model, NUTS(), 1000)
simulated = predict_session_trajectories(model, chain; save_cognitive_trajectories = SaveTrajectories(; outputs = :choice))

#The simulated choices of participant P1, for every sample
simulated[@varname(P1.choice)]

decondition_sessions takes these models too, and returns a copy whose sessions are deconditioned, since the models take the data of their sessions as arguments, which Turing.jl's decondition leaves as they are. Turing.jl's own functions then simulate the data: sample with Prior() from the prior, and predict with the parameters of each sample of a chain. They return the simulated actions and observations as variables, such as simulated_sessions[1].timesteps[3].choice.simulated, where predict_session_trajectories returns the trajectories that the sessions save. The deconditioned sessions are named simulated_sessions[i], apart from the fitted sessions, sessions[i], and a single session has the prefix simulated_session, so that predict draws every variable within them again: every action and observation, also those that the fit imputed, and what a model samples of its own, at its start or within a timestep. Turing.jl's condition and decondition work on these models as on any other, also for a variable within the sessions, such as a simulated action.

prior_predictions = sample(decondition_sessions(model), Prior(), 1000)
predictions = predict(decondition_sessions(model), chain)

Parameter recovery

condition_sessions takes these models too, with values of their variables in the collections that Turing.jl's condition takes them in: a Dict from VarNames to values, or the VarNamedTuple that rand(model) gives. It returns a copy whose sessions have the values of their actions and observations as data, such as that of simulated_sessions[1].timesteps[3].choice.simulated, and a value of any other variable is an error. DynamicPPL.subset with @varname(simulated_sessions), or with @varname(simulated_session) for a single session, leaves out the parameters of a draw from the prior of the deconditioned model, so that the copy is fitted to the simulated data, as in a parameter recovery. The sessions of the copy are named sessions[i] again once no value of theirs is simulated, and a single session keeps its prefix. Each session of the copy ends after its last timestep with a value, so a simulation that a CognitiveModeling.stopping_criterion ended is fitted with the timesteps it had. Turing.jl's condition on the same values gives the same posterior for models without a stopping criterion of their own, as the tutorial Predictive checks and parameter recovery shows, which also compares the two ways. With one, it keeps the timesteps after the last value, and the session ends where the criterion is met at the parameters of each evaluation: before its last value, which leaves out the values after it with no error, or after it, with a variable for every action and observation that follows.

deconditioned_model = decondition_sessions(model)
simulated = rand(deconditioned_model)
recovery_model = condition_sessions(deconditioned_model, DynamicPPL.subset(simulated, [@varname(simulated_sessions)]))
recovered = sample(recovery_model, NUTS(), 1000)

condition_sessions also takes the values as pairs, as Turing.jl's condition does, and the data in the forms the sessions are made from: a table of several sessions, which it reads with the column settings that the sessions were read with, such as one written from simulations, or the observations and the actions of a single session, as SessionInfo takes them. A table must have the same sessions, in the same order, since what the model was prepared with for each session must still fit.

recovery_model = condition_sessions(deconditioned_model, @varname(simulated_sessions[1].timesteps[1].choice.simulated) => true)
recovery_model = condition_sessions(model, simulated_table)
single_recovery_model = condition_sessions(single_session_model, (; reward = rewards), (; choice = choices))

Functions that a model can implement for Turing.jl

A model can add methods of these to change how it runs when it is fitted with Turing.jl, and must when it samples anything of its own, within a timestep or when it starts. They are public, but not exported.

CognitiveModeling.turing_timestep_model — Function
turing_timestep_model(model::AbstractTimestepModel, context::ModelContext)

Create a Turing.jl model for a single timestep of model, a cognitive model or an environment model, to be used as a submodel, which returns a ModelOutput. This needs Turing.jl to be loaded.

Implementation

A model can add a method of this function. The default calls timestep_model. A model which samples within a timestep needs to add a method, however; or if any other changes are desired within Turing. It must sample with ~ instead of from context.rng. Otherwise the model has a different log density each time it is evaluated. Such a model says that it samples with a method of CognitiveModeling.is_stochastic, and the default then throws an error instead of running it. The same holds for an environment model, which fitting uses to fill in observations that are ImputedMissingValue in the data: what it samples itself, such as a change of its state, must be sampled with ~, while fitting samples the observations from what it returns. A variable that is sampled on some timesteps only must be chosen by the timestep or the data, and not by the parameters or the state, since samples with different variables keep a sampler of Turing.jl from starting, or give a wrong posterior, as the page Fitting with Turing.jl describes.

Examples

using CognitiveModeling
using Turing

struct NoisyRescorlaWagner <: AbstractCognitiveModel end

#It samples noise within its timesteps
CognitiveModeling.is_stochastic(model::NoisyRescorlaWagner) = true

Turing.@model function CognitiveModeling.turing_timestep_model(
        model::NoisyRescorlaWagner,
        context::ModelContext,
    )

    ## Unpack the context ##
    #Reward observed on this timestep
    r = context.input.reward
    #Expected reward from the previous state
    V₋₁ = context.previous_state.expected_reward
    #Learning rate parameter
    α = context.parameters.learning_rate

    ## Update state ##
    #Sample the noise in the update
    ϵ ~ Normal(0, context.parameters.noise)
    #Update expected reward using the Rescorla-Wagner rule
    Vₜ = V₋₁ + α * (r - V₋₁) + ϵ

    return ModelOutput((; choice = BernoulliLogit(Vₜ - 0.5)), (; expected_reward = Vₜ))
end

turing_initialize_state(model::AbstractTimestepModel, parameters)

Implementation

A model can add a method of this function. Variables that only some samples have

Turing.jl's samplers, and its maximum_a_posteriori and maximum_likelihood, take the variables of a model from one draw from the prior. They make it with Julia's default random number generator, whatever initial_params they are given. A sample of a model of the package can have fewer variables than another in two ways.

A session can end early, when its parameters turn invalid, or when a stopping criterion is met while its data continues. The sample then has a log density of -Inf, and it doesn't have what would have been sampled after the timestep where the session ended: the actions and observations that later timesteps impute, what a model samples within a later timestep, and the variables of the downstream model, which doesn't run. A sampler rejects such samples, so every sample in the chain has every variable. But when the first draw ends early, the fit throws a KeyError that names a variable the draw doesn't have, such as KeyError: key slope not found, even when initial_params are valid. When the first draw doesn't end early but the parameters that the fit starts from do, a sampler throws an ArgumentError which says that some indices in the output vector were not set, and maximum_a_posteriori and maximum_likelihood throw an error which says that some values are missing. Valid initial_params prevent those. These errors happen less often the more seldom the priors give parameters that end a session early, and Random.seed! sets the generator that makes the first draw. A model in which nothing is sampled after a session ends has none of them.

A stopping criterion that is met already before the first timestep of a session, with its initial states and the parameters of a draw, is an error instead, which stops the fit: when the first draw gives such parameters, whatever initial_params are given, and when a sampler proposes them later. Priors under which the criterion isn't met before the first timestep prevent it.

maximum_a_posteriori and maximum_likelihood don't look for parameters to start from whose log density is finite, as the samplers do. Without valid initial_params, they can return a mode with a log density of -Inf, without an error, for any model whose priors give parameters that end a session early.

A model can also sample a variable within a timestep on some timesteps only. This is no problem when the data or the number of the timestep chooses those timesteps, as when an action that is missing in the data is imputed: every sample then has the variable on the same timesteps. When the parameters choose them, directly or through the state, samples with valid parameters have different variables, which Turing.jl's samplers don't allow for, and don't check. Sampling then either fails to start, with the same KeyError, or gives a wrong posterior without an error. In a sample that doesn't use the variable, nothing holds its value, so the sampler moves it freely, far from where its prior puts it. A sample that uses it again then has a low density, so the sampler stays among the samples that don't use it. In a test where a parameter should be above 0.5 in half of the samples, and a variable was sampled only then, the parameter was above 0.5 in at most 1 of 400. Instead, sample such a variable on every timestep, and use it only where it is needed, as for noise that is added to the expected reward Vₜ only when it is above 0.6:

noise ~ Normal(0, 0.1)
if Vₜ > 0.6
    Vₜ += noise
end

A chain sampled with Prior(), and the predictions of predict, have missing for a variable in the samples that don't have it.

Fitting several sessions

These are what the parts of CognitiveModeling.turing_full_model are written with, beside the types and functions on the pages Fitting and Parameter models. They are public, but not exported. In a Turing.jl model of several sessions, session i of CognitiveModeling.session_index has its variables under sessions[i].

CognitiveModeling.turing_parameters_model — Function
turing_parameters_model(parameters_model, sessions_info::MultipleSessionsInfo)

Create the Turing.jl model of parameters_model, a parameter model, which gives or samples the parameters of every session in sessions_info, for the cognitive model or the environment model of a turing_full_model. This needs Turing.jl to be loaded.

The model must return a NamedTuple with one entry for each parameter, named as the model names it, and a vector in each with one value for every session, in the order of the sessions. Each subtype of AbstractParametersModel that comes with CognitiveModeling.jl has a method.

Implementation

A parameter model of another kind, such as a regression, is a subtype of AbstractParametersModel with a method of this function. It can read n_sessions and the data identifiers of the sessions from sessions_info, the columns of the table that the sessions were split from, when there is one, with CognitiveModeling.session_column_values, such as the covariates of a regression, and anything else from its own fields. What it reads from the table is best read once, in a method of CognitiveModeling.prepare_parameters_model. The full model treats it as one that samples, so that with it the environment of every session runs, and the observations in the data inform the environment's parameters.
